# v0.14.0 backport plan — main → the four support lines (2026-08-27)

Ports the v0.13.1..main delta to every supported line ahead of the five-line
v0.14.0 release. Written per the v0.14.0 program; reviewed by a 2-Opus panel
before implementation (fold recorded in §8).

## 2. Why #256 is not a backport item

- The `line.env` flip and the `ReleaseWorkflowContractTest` value pin are
  line-local identity. 26.1 already carries its own equivalent (`430bc369` —
  one commit AFTER the `v0.13.1+mc26.1` tag at `ffbeae7e`). 1.21.1 has shipped
  NeoForge since v0.11.0. 1.21.11 and 1.21.10 stay `LINE_SHIP_NEOFORGE=false`
  (no Voxy client route) — their existing `false` pins with the v0.11.0
  comment remain CORRECT on those lines (verified on-branch: no line's
  contract test reds after the three picks, and no picked hunk references
  `release-neoforge`/`LINE_SHIP_NEOFORGE`).
- `release-neoforge.yml` is a one-off backfill utility for already-released
  tags; v0.14.0 ships NeoForge through the normal `release.yml` wherever the
  line flag is true. It exists exactly where it was needed (main,
  26.1-v0.13); 1.21.1 never needed a backfill. Porting it to non-shipping
  lines would add a workflow whose guards make every dispatch a no-op.
- Phase-C note: v0.14.0+mc26.1 is the first 26.1 release whose NeoForge jar
  ships through `release.yml` itself (v0.13.1+mc26.1's was backfilled) — a
  release-notes fact, not a backport item.

## 4. Mechanics

Per line, in a dedicated git worktree (`.claude/worktrees` NOT used — plain
`git worktree add ../lss-port-<line>` outside the repo so gradle caches stay
per-tree), cherry-pick each PR as ONE squashed unit in merge order:

```
git cherry-pick -m 1 ef408622   # #243 two-axis cache keying
git cherry-pick -m 1 5f4275ab   # #244 service gate
git cherry-pick -m 1 8856204f   # #258 folia hardening
```

`-m 1` is verified correct for all three merges (parent 1 is the mainline in
each; the PRs' internal "Merge branch 'main'" commits sit on the second-parent
side and collapse away). One commit per PR per line keeps the port reviewable
(`git range-diff` and a plain `git diff <base>..HEAD` vs
`git diff 805560c2..main` comparison). Conflicts are resolved in-pick;
per-line adaptations beyond conflict resolution get a fourth `port(<line>):`
commit so review can see adaptation separate from transplant.

Port order: **26.1 → 1.21.11 → 1.21.10 → 1.21.1**. Measured divergence over
the 97 delta-touched files (line blob vs `805560c2`): **41 / 47 / 54 / 58**
files respectively — ascending, and each resolved conflict becomes the
reference for the next line.

**Measured conflict set** (merge-tree dry runs per pick per line; pick-3
predictions on the 1.21.x lines are approximate because the dry run cannot
chain picks — `ServiceGateState.java`/`PaperServiceGateSweepTest` "conflicts"
are pure artifacts of that, with zero conflict markers):

## 5. Known per-line adaptation points

### 5.1 PR #243 (two-axis cache keying)
- New files (WorldSubKey, CacheKeyAliases, AliasCorroboration, AliasLatch,
  ClientWorldSeed, VoxyStorageOverride, AccessorBiomeManager + tests): add
  without conflict everywhere, BUT three of the new test files carry 26.x-only
  spellings that do not compile on 1.21.10/1.21.1 — see §5.5.
- `AccessorBiomeManager` reads `biomeZoomSeed` — Mojang mappings, stable
  across 1.21.1..26.2; `SeedAccessorContractTest` pins it reflectively per
  line at Tier 1.
- **`LSSClientCommands` (the one #243 conflict on 1.21.11/1.21.10/1.21.1):**
  main's side uses fabric-api's `ClientCommands` class, which does not exist
  on the older lines' fabric-api — resolve by taking main's
  `ClientCommandActions.resetSubtree(...)` call **bound to
  `ClientCommandManager::literal`** (the line's own class). 26.1 merges clean.
- **`VoxyCompat` (the one #243 conflict on ALL four lines):** #243 changed the
  reset-ladder call arity (`}), forceWipe, grantedLiveRoot);`) inside a block
  whose body is line-specific — every support line uses
  `Minecraft.getInstance().levelRenderer.allChanged()` where main's 26.2 uses
  `levelExtractor.allChanged()`, and main's hunk carries the `levelExtractor`
  lines as context. Resolution: keep the line's `levelRenderer` body, take
  main's new arguments AND the new `probeStorageProduction()` method. A
  take-theirs reintroduces `Minecraft.levelExtractor`, which does not exist on
  any support line (compile-loud).
- 1.21.1 only: the Voxy storage probe targets mainline Voxy internals; on
  1.21.1 the client pairing is the j-shelfwood NeoForge port / m3t4f1v3 fork.
  The probe is reflective and fails toward "no corroboration" (aliases stay
  off) — port verbatim, note the behavior in the port commit, do NOT invent
  fork-specific probing.

## 6. Gates (support-tier budget: correct, not perfect)

Per line, serially (never two gradle builds at once on this box; never beside
a soak):
0. `python3 scripts/release_check.py --selftest && python3 scripts/check_soak.py --selftest
   && python3 scripts/soak_report.py --selftest && bash -n scripts/soak.sh`
   (the port edits release_check.py and soak.sh; every line's build.yml runs
   these selftests, so catch a bad resolve BEFORE the push)
1. Tier 1 — `./gradlew :fabric:test -x runGameTest -x runClientGameTest`,
   EXCEPT on 1.21.1: `./gradlew :fabric:test -x runGameTest` (Tier 3 is CUT
   there — `enableClientGameTests = false`, the task is not registered and
   `-x runClientGameTest` FAILS the invocation)
2. Tier 2 — `./gradlew :fabric:runGameTest`
3. `./gradlew :paper:test`
4. `./gradlew :neoforge:build` (contract tests; module builds on every line)

PRECONDITION on the JAVA_21 lines (1.21.11, 1.21.10, 1.21.1): build with a
Java 21 JDK — their banners state it unconditionally (paperweight's codebook
cannot parse Java 25 class files). Full five-line
release pre-flight (incl. `release_check.py --version`) is Phase C, not here —
but any red here blocks Phase C.

Timing-flake triage per the CLAUDE.md flake catalog: waitFor-timeout shapes
re-run once isolated; logic-assertion reds are real.

## 7. Review protocol and push discipline

- This plan: 2-Opus panel before implementation; fold in §8.
- Per line after implementation: the port is "non-trivial" if any pick
  conflicted or a `port(<line>)` commit exists — expected for all four lines;
  each non-trivial line gets its own 2-Opus review of
  `git diff <base>..HEAD` against main's `git diff 805560c2..main`, checking:
  (a) nothing dropped or mistranslated, (b) adaptations match the line's
  facts (esp. the §5.2 polarity and §5.4 identity traps), (c) no main-only
  identity leaked, (d) the new tests came along and pass.
- NOTHING is pushed until the line's review folds. Then push all four
  branches (build.yml covers support/**; its gametest tiers retry once).
  NOTE: `build.yml` has `paths-ignore` for `**.md`/`docs/**` — a docs-only
  `port(<line>)` commit at the branch tip produces NO CI run; don't read that
  absence as green.
- v0.14.0 version scrubs, release notes, and tags are Phase C — the port
  branches stay at mod_version 0.13.0 until then. (Phase-C reminder, learned
  at v0.12.0: push the five release tags ONE AT A TIME — a single push with
  >3 tags fires zero workflow events.)
